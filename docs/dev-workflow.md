# First-party mod development and release workflow

Canonical document to create, iterate, and package mods under the
studio's brand (`Leteo Works`) that live in the
[`game-mods/`](https://github.com/leteoworks/my-game-fw-mods)
subrepo and consume the `@modules/moddable/*` framework family.

> Prerequisite reading (5 min): subrepo README + the
> `@modules/moddable` README.
>
> For a generic intro to the mod system (without assuming the
> `game-mods/` subrepo), see [getting-started.md](getting-started.md).
> This doc assumes first-party studio mods.
>
> To **manually test the mod end-to-end** like a Steam user
> would (activate → use sliders → see effect), see
> [manual-testing-flow.md](manual-testing-flow.md).

---

## TL;DR — the cycle in one line

```
create mod at game-mods/<gameId>/<modId>/  →  pnpm dev:mod <gameId> <modId>  →  edit src/  →  see change in browser
```

And for release:

```
pnpm build:game <gameId> --mode=electron   # sign + bundle + Electron in one
```

The framework takes care of discovering, compiling, signing, and
bundling all the mods of `game-mods/<gameId>/` automatically.

## 1. Workflow architecture

```
┌────────────────────────────────────────────────────────────────┐
│  Subrepo: game-mods/  (separate repo, git submodule)           │
│                                                                │
│  game-mods/snake-classic/studio.gameplay-tuner/                │
│    ├── mod.json                                                │
│    ├── src/index.ts        ← you edit here                     │
│    ├── locales/en.json                                         │
│    ├── package.json                                            │
│    ├── build.mjs           ← esbuild (--watch in dev)          │
│    └── dist/mod.js         ← IIFE ES2020 bundle (generated)    │
└────────────────────────────────────────────────────────────────┘
                                  │
                                  │  webpack alias: @game-mods/* → ./game-mods/*
                                  ▼
┌────────────────────────────────────────────────────────────────┐
│  Parent repo: my-game-fw-mods-main                             │
│                                                                │
│  src/games/snake-classic/mods/                                 │
│    ├── tunables.ts          ← declares what can be tuned       │
│    ├── moddable-config.ts   ← consumes @modules/moddable family│
│    ├── policy.ts            ← single bridge to @modules/mod-runtime
│    └── bundled-loader.ts    ← AUTO-DISCOVERS mods via import.meta.glob
│                                                                │
│  src/games/snake-classic/mods/bundled-mods-manifest.json       │
│    ← AUTOGENERATED by scripts/build-game-mods.mjs              │
│      with sha256 + signature (release builds only)             │
└────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
                       Electron / web / mobile builds
                       (all consume the same source)
```

**Key rules of this workflow**:

1. **One source of truth per mod**: `game-mods/<gameId>/<modId>/`.
2. **The parent does NOT contain mod code** — only game wiring
   (`policy.ts`, `moddable-config.ts`, `bundled-loader.ts`).
3. **Automatic discovery**: `bundled-loader.ts` uses
   `import.meta.glob` on the `@game-mods/*` alias — adding a mod
   doesn't require touching game code.
4. **Auto-generated manifest**: `bundled-mods-manifest.json` is
   not hand-edited; `scripts/build-game-mods.mjs` writes it with
   fresh sha256 on every build.
5. **Signing release-only**: dev and regular `build` skip
   signing; the runtime accepts `signed: false` when
   `NODE_ENV !== 'production'`. CI guard
   `pnpm exec node scripts/mods/check-bundled-mods-signed.mjs`
   rejects committing a manifest with `signed:false` on `main`/`dev`
   branches (§2.5 audit 2026-05-24).
6. **Single source of the bundled list**: the script emits
   `BUNDLED_MOD_IDS` in `bundled-mods-sources.generated.ts`; the
   game's `policy.ts` imports from there instead of re-declaring
   the list (§2.4 audit 2026-05-24). Impossible for order, ids,
   or count to drift between the manifest and the
   `defineModPolicy`.

## 2. How to create a new mod (5 steps)

Assuming a mod-compatible game already exists in the framework
(as of 2026-05, only Snake Classic is). Steps for the example
`studio.colorful-snake`:

### Step 1 — Scaffold

```bash
cd game-mods/snake-classic
cp -r studio.gameplay-tuner studio.colorful-snake
cd studio.colorful-snake
```

Edit identification fields in `mod.json`:

```diff
- "id": "studio.gameplay-tuner",
+ "id": "studio.colorful-snake",
- "version": "0.1.0",
+ "version": "0.1.0",
  "target": {
    "gameId": "snake-classic",
    "gameVersion": "^1.0.0"
  },
  ...
  "metadata": {
-   "name": "Gameplay Tuner",
+   "name": "Colorful Snake",
-   "description": "...",
+   "description": "Swappable color palettes for Snake.",
  }
```

> **Important**: the `id` must be unique across ALL mods (of all
> games). Convention: `<vendor>.<short-id>` in kebab-case.

### Step 2 — Implement logic

Edit `src/index.ts`:

```ts
import { applyConfigurationToGame } from './apply-config';
import { buildSettingsTabDescriptor } from './settings-tab';

host.registerSettingsTab?.(buildSettingsTabDescriptor());

host.subscribeEvent('GAME_STARTED', async () => {
  // your logic
});

host.log.info('[colorful-snake] loaded');
```

Game access is via `host.callHostFn(name, args)` — the available
host fns come from the target game's `moddable-config.ts`.
Canonical list:

- `gameConfigSet({ name, value })` — sets a declared tunable.
- `gameConfigReset({ name })` — restores the default.
- `gameConfigSnapshot()` — reads all current tunables.

If you need tunables the game DOESN'T expose yet:

1. Edit `src/games/<gameId>/mods/tunables.ts` in the parent repo
   adding the `defineTunable(...)` you need.
2. (Optional) codemod gameplay code to read `tunable.get()`.
3. Bump `hostApiVersion` in `moddable-config.ts` (MINOR if you
   add, MAJOR if you break).

### Step 3 — Locales

Edit `locales/en.json` and `locales/es.json`:

```json
{
  "mod-colorful-snake.tab.title": "Colorful Snake",
  "mod-colorful-snake.palette.label": "Palette",
  ...
}
```

The namespace declared in `mod.json` (`permissions[type=i18n].namespaces`
field) must match the key prefix. If a locale is incomplete, CI
will detect it (`pnpm exec node scripts/mods/validate-i18n.mjs`).

### Step 4 — Test in dev

```bash
cd /Users/aicampos/Documents/Antonio/code/github_projects/my-game-fw-mods-main
pnpm dev:mod snake-classic studio.colorful-snake
```

That starts two concurrent processes:
- `esbuild --watch` inside the mod → regenerates `dist/mod.js` on
  each change.
- `pnpm dev:game snake-classic` → Quasar dev for the game. HMR
  detects the raw bundle change and `ModRuntime` re-evaluates the
  mod in the sandbox (without reloading the browser, unless
  structural changes).

Single terminal, ~1-2s latency between edit and seeing the
result.

### Step 5 — Commit + push the mod

When the mod is stable:

```bash
cd game-mods
git add snake-classic/studio.colorful-snake
git commit -m "feat: studio.colorful-snake v0.1.0"
git push
cd ..

# Bump the submodule SHA in the parent:
git add game-mods
git commit -m "chore(game-mods): bump submodule (studio.colorful-snake v0.1.0)"
```

The subrepo's push is independent of the parent's push —
coordinate both when the mod is ready for release.

## 3. How to test in dev (detail of `pnpm dev:mod`)

```bash
pnpm dev:mod snake-classic studio.gameplay-tuner
```

Equivalent to:

```bash
# Single terminal, two concurrent processes via concurrently.
node scripts/dev-mod.mjs snake-classic studio.gameplay-tuner

# Internally:
#  1. Validates that game-mods/snake-classic/studio.gameplay-tuner/ exists.
#  2. pnpm install inside the mod (idempotent, ~10s first time, ~0 later).
#  3. Launches:
#       a) pnpm --filter <mod-path> watch    (esbuild --watch)
#       b) pnpm dev:game snake-classic       (Quasar dev for the game)
#  4. Terminates both on Ctrl-C.
```

**What you see on screen**:

```
[dev-mod] watching game-mods/snake-classic/studio.gameplay-tuner/
[esbuild]  build OK (143ms)
[quasar]   READY  Quasar dev server running at http://localhost:9000
[quasar]   compiled in 4321ms

  # you edit src/index.ts...
[esbuild]  build OK (87ms)
[quasar]   hmr update src/games/snake-classic/mods/bundled-loader.ts
[mod-runtime] mod studio.gameplay-tuner re-evaluated
```

### Useful variants

```bash
# Multiple mods at once:
pnpm dev:mod snake-classic studio.gameplay-tuner studio.colorful-snake

# All mods of the game:
pnpm dev:mod snake-classic --all

# Only the game (without mod watch — useful if mods are already in dist/):
pnpm dev:game snake-classic
```

### Dev mode vs regular build vs build:release

| Mode | Command | Sign mods | Manifest | sha256 |
|---|---|---|---|---|
| Dev | `pnpm dev:game <id>` or `pnpm dev:mod ...` | ❌ skip | auto-generated (no sig) | computed but not enforced |
| Regular build | `pnpm build:game <id>` | ❌ skip | auto-generated (no sig) | computed |
| Release | `pnpm build:game <id> --mode=electron` (or `--release`) | ✅ Ed25519 | auto-generated (with sig) | enforced |

The mod runtime accepts `signed: false` in non-release builds;
in release it requires valid signature (the loader rejects mods
with `mod.signature.value === undefined` or sha256 mismatch).

## 4. How to build for Electron with N mods

Single command:

```bash
pnpm build:game snake-classic --mode=electron
```

What happens, in order:

```
1. scripts/build-game-mods.mjs (pre-build hook):
   ├── Discover: glob game-mods/snake-classic/*/mod.json
   ├── For each mod:
   │   ├── pnpm install (if node_modules doesn't exist)
   │   ├── pnpm build:release (esbuild --minify → dist/mod.js)
   │   └── sha256(dist/mod.js)
   ├── If NODE_ENV=production or --release:
   │   └── Sign each dist/mod.js with the studio's Ed25519 key
   │       (env var GAMEFW_MODS_SIGN_KEY; mandatory in release).
   └── Writes src/games/snake-classic/mods/bundled-mods-manifest.json
       with all entries (modId, version, sha256, signedBy,
       signedAt, signed, sig).

2. quasar build --mode=electron:
   ├── Webpack resolves alias @game-mods/* → game-mods/*
   ├── bundled-loader.ts runs import.meta.glob('@game-mods/snake-classic/*/dist/mod.js')
   │   → webpack inlines each mod.js as ?raw in the game's bundle
   ├── Tree-shaking eliminates the unreferenced
   └── electron-builder packages the bundle + assets

3. Output: dist/electron/snake-classic-1.x.x-{mac,win,linux}.{dmg,exe,AppImage}
```

**N mods**: the script automatically discovers all mods in
`game-mods/snake-classic/`. Adding mod #7 = `mkdir` + `cp -r` and
that's it. Zero framework code.

**Other games?** Same flow. `pnpm build:game pong --mode=electron`
looks in `game-mods/pong/*/` (when Pong becomes mod-compatible).

### Variants

```bash
# Build for web (no Electron):
pnpm build:game snake-classic

# Build for iOS (Capacitor). Mod-free MANDATORY for App Store —
# all mods are automatically omitted, the quasar.config.js alias
# swap redirects @modules/moddable/* and @modules/mod-runtime
# to no-op stubs:
pnpm build:game snake-classic --mode=capacitor --target=ios

# Steam standalone wrapper build (Classics Collection):
pnpm build:collection --mode=electron
# (includes ALL mods of ALL gameIds present in the wrapper)
```

## 5. Cryptographic signing

### Policy

- **Dev / regular build**: NO signing. Manifest stays with
  `signed: false` and `sig: null`. The runtime accepts these
  mods only when `process.env.NODE_ENV !== 'production'`.
- **`build:release`** (i.e. `--release` or `--mode=electron` or
  `NODE_ENV=production`): signing MANDATORY. If
  `GAMEFW_MODS_SIGN_KEY` env is not present, the build aborts.

### Technical details

Algorithm: **Ed25519**. Private key lives in:
- Local: env var `GAMEFW_MODS_SIGN_KEY` (base64 PKCS#8).
- CI: GitHub Actions secret with the same name.

The signed payload is the canonical JSON of the manifest without
the `signature` field, with keys recursively ordered alphabetically
+ `metadata.bundleHash = sha256(dist/mod.js + locales/ + assets/)`.
The runtime (`src/modules/mod-runtime/trust/verify-signature.ts`)
verifies this on every load.

### Key rotation

`scripts/mods/sign-bundled-mods.mjs --rotate-key <newKeyId>`
generates a new pair, signs with the NEW one, archives the old
one in `scripts/mods/trust-keys/archive/`. The runtime accepts
the full active key set + the archived ones within a grace
window (defined in `@modules/mod-runtime/trust/keys.ts`).

## 7. Troubleshooting

### "Change in `src/index.ts` doesn't show in browser"

1. Verify `esbuild --watch` is running (`ps aux | grep esbuild`).
2. Look at `game-mods/<gameId>/<modId>/dist/mod.js` — the mtime
   should update on save.
3. If HMR doesn't fire, look at the Quasar console — sometimes it
   needs a hard reload (Cmd-Shift-R) when the mod structure
   changes (e.g. you add a new event subscription).

### "`pnpm build:game` fails with `GAMEFW_MODS_SIGN_KEY missing`"

If you didn't want to release but want a signed build, export the
key temporarily:

```bash
export GAMEFW_MODS_SIGN_KEY="$(cat ~/.leteoworks-keys/mod-sign-2026-01.b64)"
pnpm build:game snake-classic --mode=electron
```

If you wanted a build without signing (local Electron dev):

```bash
pnpm build:game snake-classic --mode=electron --no-sign-mods
# or
GAMEFW_MODS_SKIP_SIGN=1 pnpm build:game snake-classic --mode=electron
```

### "Mod appears in manifest but doesn't load"

1. Verify `mod.json` declares `target.gameId` = correct game ID
   and `target.gameVersion` matches the compatible range.
2. Verify `target.engine.preferred` is in the `engines` list
   declared in the game's `policy.ts`.
3. Look at `host.log` and DevTools console — the runtime logs
   rejections with reason (`MOD_REJECTED_*`).

### "Glob doesn't discover my new mod"

`import.meta.glob` in webpack is lazy in HMR. After creating a
NEW mod folder, it usually requires a Quasar dev restart
(Ctrl-C + `pnpm dev:game ...`). Edits inside existing folders do
refresh hot.

### "Submodule conflict: parent SHA points to nonexistent commit"

The subrepo push must happen BEFORE the parent commit. If you
skipped the push:

```bash
cd game-mods && git push && cd ..
# Now the SHA referenced in the parent exists in remote.
```

## 8. FAQ

**Why two repos (parent + subrepo `game-mods/`)?**
So mods evolve at a different pace from the framework and game.
Game bump ≠ mod bump ≠ framework bump. Separate repos =
independent SemVer + clean history.

**What if I want to see the mod commit log on GitHub alongside the game?**
Submodules do exactly that: the parent references the subrepo SHA
and GitHub shows the submodule delta in each parent commit.

**Can I develop a mod in a fork of the subrepo?**
Yes — anyone can clone `leteoworks/my-game-fw-mods`, create their
mod in `<gameId>/<vendor>.<id>/`, and submit a PR. Third-party
contributor mods go through `workshopVerified` signing (not
`studioSigned`).

**What about third-party mods (Workshop)?**
NOT in `game-mods/`. They live in Steam Workshop or are sideload.
`game-mods/` is exclusive to the studio. The distinction matters
for trust tier:
- `game-mods/` → always `studioSigned`.
- Workshop → `workshopVerified` or `unsigned` per policy.

**Do I have to run `pnpm install` in every mod?**
The first time yes (esbuild as devDep). The `dev:mod` script does
it automatically, idempotent. After that, only if you update the
mod's `package.json`.

**How do I unit-test the mod?**
Each mod can have its own `__tests__/` and `pnpm test` inside the
mod. Vitest or jest, whichever you prefer. The `@modules/moddable/*`
family provides the HostBridge types for mocking from tests.
